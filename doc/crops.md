# Crops: per-region screenshot extraction

## Why crops exist

Full-page comparison of Flutter screenshots against a reference design is an
unreliable signal. The typical failure mode looks like this: a dashboard is
rendered at 1440x900 logical pixels, the golden PNG is 2880x1800, and the
compare step rescales both sides to some smaller resolution so the diff fits
in memory or in a review tool. Icons blur into their backgrounds. Border
colors average with adjacent pixels. Four pixel spacing errors disappear
into compression noise. The loop never converges on fine detail because the
detail is gone before the comparison starts.

Crops solve this by letting the user declare the regions that matter and
extract them from the generated golden at native resolution. Each named
region is written as its own PNG, and each region is compared against a
matching reference crop of the same dimensions. A 160x80 badge is compared
as 160x80, not as eight blurred pixels inside a downscaled thumbnail.

Crops are a sidecar output. The full-page golden still exists and is still
the primary artifact. Crops live alongside it and are consumed by
`print_widget compare`.

## Two ways to define crops

A `PrintEntry` exposes two fields:

| Field        | Type                  | Use when                                           |
|--------------|-----------------------|----------------------------------------------------|
| `crops`      | `Map<String, Rect>?`  | You know the regions up front and want them inline |
| `cropsFrom`  | `String?`             | Regions come from a smart-extract JSON index file  |

Inline definition looks like this:

```dart
PrintEntry(
  name: 'dashboard',
  builder: (_) => const DashboardPage(),
  devices: [DeviceFrame.web1440],
  crops: {
    'header':   Rect.fromLTWH(0, 0, 1440, 80),
    'sidebar':  Rect.fromLTWH(0, 80, 240, 820),
    'main':     Rect.fromLTWH(240, 80, 1200, 820),
  },
)
```

The JSON-driven form looks like this:

```dart
PrintEntry(
  name: 'dashboard',
  builder: (_) => const DashboardPage(),
  devices: [DeviceFrame.web1440],
  cropsFrom: 'design/dashboard/_index.json',
)
```

When both fields are set on the same entry, `cropsFrom` wins. This is
deliberate: the JSON file is usually regenerated by an extraction tool, and
a stale inline map should never silently override fresh data. Document this
with a comment in code if it matters to your team.

## Coordinate system

Crop rectangles are expressed in **logical pixels**, matching the
`DeviceFrame.size` of the entry. Before slicing, the CLI multiplies each
rect by the frame's `pixelRatio` to get physical coordinates in the golden
PNG.

Worked example: a `DeviceFrame` with `size: Size(1440, 900)` and
`pixelRatio: 2.0` produces a physical PNG of 2880x1800. A header defined as
`Rect.fromLTWH(0, 0, 1440, 80)` is sliced from the physical PNG at
`(0, 0, 2880, 160)`.

| Logical rect (LTWH)          | pixelRatio | Physical rect (LTWH)          |
|------------------------------|------------|-------------------------------|
| `(0, 0, 1440, 80)`           | 2.0        | `(0, 0, 2880, 160)`           |
| `(240, 80, 1200, 820)`       | 2.0        | `(480, 160, 2400, 1640)`      |
| `(0, 0, 375, 64)`            | 3.0        | `(0, 0, 1125, 192)`           |

If you declare rects in physical pixels by accident, the extracted regions
will be too small and offset. Always treat the numbers as matching the
layout you wrote in Dart.

## Clamping and offscreen behavior

Rectangles that extend beyond the image are clamped to image bounds. A rect
`(1300, 0, 400, 80)` on a 1440x900 frame becomes `(1300, 0, 140, 80)` in
logical space. The extracted PNG will be narrower than requested, but it
will not crash and it will not produce garbage pixels.

Rectangles that are entirely offscreen are skipped. The CLI writes a
warning to stderr and continues processing the remaining crops:

```
warning: crop 'footer' on entry 'dashboard' is fully offscreen
         (rect=Rect.fromLTWH(0, 2000, 1440, 80),
          imageSize=2880x1800), skipping
```

This distinction matters: silent success on a bad crop would cause the
compare step to pass against a zero-byte PNG. Silent failure would hide a
stale coordinate file. Loud warning plus skip is the middle ground.

## Output layout

Crops are written into a `crops/` subdirectory under the entry's output
folder:

```
test/prints/output/
  dashboard/
    web_1440.png              # full-page golden
    crops/
      header.png
      sidebar.png
      main.png
```

`flat: true` mode still writes crops into a per-entry subfolder because
flat naming would collide on region names. Crops are excluded from
`manifest.json` — they are sidecars, not primary screenshots, and manifest
consumers should continue to see one entry per device.

## JSON format for `cropsFrom`

The file is a JSON array of region objects:

```json
[
  { "file": "01-header.png",  "x": 0,    "y": 0,   "w": 1440, "h": 80  },
  { "file": "02-sidebar.png", "x": 0,    "y": 80,  "w": 240,  "h": 820 },
  { "file": "03-main.png",    "x": 240,  "y": 80,  "w": 1200, "h": 820 }
]
```

| Key      | Required | Notes                                                        |
|----------|----------|--------------------------------------------------------------|
| `file`   | yes      | Filename for the crop. Extension is stripped to form the name |
| `x`      | yes      | Logical x origin                                             |
| `y`      | yes      | Logical y origin                                             |
| `w`      | yes      | Logical width (alias: `width`)                               |
| `h`      | yes      | Logical height (alias: `height`)                             |

Names are derived from `file` by stripping the extension: `01-header.png`
becomes `01-header`. The generated crop is written as `01-header.png` in
the `crops/` directory, which means it pairs directly against a reference
of the same name.

## End-to-end example

A dashboard entry with three regions:

```dart
// print_widget/config.dart
final printSession = PrintSession(
  appWrapper: (child) => MaterialApp(home: child),
);

final printList = <PrintEntry>[
  PrintEntry(
    name: 'dashboard',
    builder: (_) => const DashboardPage(),
    devices: [DeviceFrame.web1440],
    crops: {
      'header':   Rect.fromLTWH(0,   0,    1440, 80),
      'sidebar':  Rect.fromLTWH(0,   80,   240,  820),
      'main':     Rect.fromLTWH(240, 80,   1200, 820),
    },
  ),
];
```

Generate and list the output:

```bash
print_widget generate --name=dashboard
```

Resulting layout:

```
test/prints/output/
  dashboard/
    web_1440.png
    crops/
      header.png
      sidebar.png
      main.png
    .reference/
      crops/
        header.png
        sidebar.png
        main.png
```

Then compare against the references:

```bash
print_widget compare --name=dashboard --threshold=0.97
```

## Writing reference crops

References live at `<outputDir>/<entry>/.reference/crops/` and must match
the generated crop filenames one-to-one. How they get there depends on the
workflow:

| Source                    | How references arrive                                    |
|---------------------------|-----------------------------------------------------------|
| Figma export              | MCP or manual download into `.reference/crops/`           |
| Lovable / smart-extract   | Extract script writes crops directly to `.reference/crops/` |
| Hand screenshot           | `cp` into `.reference/crops/` with the expected name      |
| Previous golden           | `cp crops/*.png .reference/crops/` to freeze a baseline   |

Reference and generated crops must share dimensions, otherwise compare
fails fast (see viewport.md).

## Gotchas

- A `DeviceFrame` with `pixelRatio: 1.0` used for the reference and `2.0`
  for the Flutter render will produce valid-looking crops that never
  converge. Use the same frame on both sides.
- `crops` is silently ignored when both it and `cropsFrom` are set. If you
  see unexpected regions, check whether a JSON file is also pointed at.
- Crop extraction only runs when `crops` or `cropsFrom` is non-null on the
  entry. Entries with neither field work exactly as before and produce no
  `crops/` directory.
- Coordinates that came from a Figma frame at a different size than your
  `DeviceFrame` will all be off by the ratio. Rescale the JSON file before
  setting `cropsFrom`, do not adjust `pixelRatio`.

## API reference

Implementation lives in `lib/src/crops.dart`. The following symbols are
public to the runner and CLI:

| Symbol                | Kind     | Purpose                                                         |
|-----------------------|----------|------------------------------------------------------------------|
| `CropRegion`          | class    | In-memory representation: `name`, `rect`, optional source file   |
| `loadCropsFromJson`   | function | Reads a `cropsFrom` JSON file and returns `List<CropRegion>`     |
| `cropsFromMap`        | function | Converts `Map<String, Rect>` into `List<CropRegion>`             |
| `writeCropsToDisk`    | function | Slices physical pixels from a loaded PNG and writes each region |
| `processEntryCrops`   | function | Top-level: resolves precedence, applies `pixelRatio`, clamps, writes |

Both the CLI path (via the generated temp test) and the standalone runner
API call into `processEntryCrops`, so crop behavior is identical regardless
of how generation was triggered.
